## Why this release matters (plain-language summary)

v1.3.0 is **not** about adding new rules. It's about making KubePreflight's existing results more trustworthy.

**The problem, concretely:**

A live scan reports a `WH-005` finding on an admission webhook. Later, someone runs a `--manifests-only` scan — which never evaluates `WH-005` at all, because it has no live cluster to inspect. Today, `compare` sees the `WH-005` finding present in the baseline and absent from the current scan, and reports it as **Resolved**. Nothing was actually fixed. The rule simply never ran a second time.

**The one-line release goal:**

> v1.3.0 ensures that KubePreflight never confuses "not checked" with "safe," and never confuses "not re-evaluated" with "resolved."

**What changes for an operator, concretely:**

Today:

```text
Readiness Score: 92
No WH-005 finding
```

Reads as "safe." After v1.3.0:

```text
Readiness Score: 92
Evaluation Coverage: Partial
WH-005: Not evaluated
Reason: live Kubernetes admission webhook data unavailable
```

An operator can no longer approve an upgrade on false confidence produced by a rule that silently didn't run.

**What v1.3.0 achieves, in five parts:**

1. **Trust in evidence** — every important conclusion's source is clear: live Kubernetes API, manifest, AWS/EKS API, compatibility catalog, or derived analysis.
2. **Unknown is never rendered as safe** — six states stay distinguishable: evaluated-and-clean, finding-detected, not-applicable, not-evaluated, insufficient-evidence, evaluation-failed.
3. **Compare becomes reliable** — `baseline finding + current rule evaluated + finding absent = Resolved`, but `baseline finding + current rule not evaluated = Not re-evaluated`. These must never collapse into the same bucket.
4. **Every surface agrees** — Terminal, JSON, Markdown, HTML, and Console must never disagree about the same scan's evaluation state (e.g. HTML saying "category unavailable" while Terminal says "passed" and Console says "partial" and compare says "resolved," all for the same underlying scan).
5. **Foundation for repeat usage** — teams running KubePreflight as a recurring habit (daily/scheduled scans, weekly reviews, pre-upgrade scans, post-remediation rescans, post-upgrade comparisons) need the tool to correctly answer "what changed, what resolved, what's still present, and what wasn't even checked this time." v1.3.0 builds that foundation — not the scheduling/history/notification/ownership features themselves.

**Explicitly not in v1.3.0:** a scheduled-scan engine, a history database, Slack/email notifications, finding ownership, an accepted-risk workflow, AI-based confidence scoring, automatic upgrade approval, or automatic remediation. These are later-phase concerns; see "Regular-usage foundation" and "Deferred and rejected items" below for exactly what's foundation-only versus deferred versus rejected.

This may read as a small, technical release. For a product whose value depends on being trusted for *repeated* use, it is not — a tool that occasionally tells an operator "safe" when it actually means "didn't check" cannot be the standard operational habit the product is trying to become.

## Executive decision

**APPROVED as recommended.** The reviewer approved shipping the narrow v1.3.0 scope described below in a single release, without splitting the main capability across releases. The release thesis is recorded verbatim as the governing sentence for every decision in this document:

> KubePreflight must distinguish "a rule evaluated successfully and found nothing" from "a rule was not evaluated or lacked sufficient evidence."

**Recommendation (as approved): ship a narrow v1.3.0 that adds one new concept — per-rule/per-check *evaluation state* — layered on top of the existing `ScanCoverage` model, without touching rule IDs, severities, upgrade gates, fingerprints, or the frozen v1 schemas.**

The audit confirms the product already has real, working "don't guess" infrastructure (`ScanCoverage`, `EKSAddonInfo.VerificationUnavailable`, the rollback provenance/freshness gate, `compatcatalog.StatusUnknown`, `apicatalog` range rejection). What it does **not** have is a way to say, at the rule or finding-category level, "this specific check did not run" — today that state is either (a) invisible (most rules), (b) inferable only from `ScanCoverage.AWS/Kubernetes.Status == partial`, which is a *plane*-level signal, not a *rule*-level one, or (c) silently indistinguishable from "ran, found nothing." `internal/comparison` inherits this gap directly: it has zero notion of rule execution and will happily report a finding as `Resolved` when the real cause was "the rule never ran in the second scan" (`internal/comparison/compare.go:70-74`).

The smallest coherent v1.3.0 contract is therefore: **add an explicit per-rule execution/applicability record to the report, thread it through every renderer's existing "assessment incomplete" affordance (already built for `partial` coverage), and make `compare` consult it before calling anything `Resolved`.** This is additive to the JSON schema, requires no rule-ID/severity/gate/fingerprint change, and is a direct, minimal foundation for "what changed since last scan" in later releases — without building history storage, notifications, or ownership now.

Confidence in this recommendation: **high** for the problem statement (multiple independent gaps converge on the same root cause), **medium** for the exact field shape (see "Candidate data-model options" — three viable shapes exist; Phase 4 recommends one but flags the decision as still open for reviewer input).

## Product goal alignment

KubePreflight's stated long-term goal is to become "the standard, repeatable EKS operational-safety habit before and after platform changes." The regular workflow this implies (Baseline → scheduled scan → change detection → upgrade planning → pre-change approval → remediation verification → post-upgrade verification → rollback assessment → retained evidence) depends on **trusting a delta between two scans**. A delta is only trustworthy if "nothing changed" and "we stopped being able to check" are distinguishable. Today they are not, at the rule level (confirmed in "Confirmed product gaps" below). This is the direct product justification for v1.3.0's theme, "Evidence Integrity and Evaluation Semantics" — it is not a nice-to-have refactor, it is the specific precondition the regular-usage workflow needs and does not yet have.

The audit also confirms the codebase's own internal principle already points this direction. `docs/v1-compatibility-contract.md:154-164` states as a *stable v1 guarantee*: "KubePreflight must not guess safety from missing evidence... Missing provider enrichment is coverage behavior, not proof of safety." v1.3.0's job is to extend this already-adopted principle from the plane level (`ScanCoverage`) down to the rule level, and from single-scan rendering into `compare`/`gate` — not to invent a new philosophy.

## Current implementation baseline

### Finding model — `internal/findings/finding.go`

- `Severity` (`Blocker`/`Warning`/`Info`, lines 17-21), `ConfidenceTier` (`STATIC_CERTAIN`/`PROVIDER_REPORTED`/`OBSERVED`/`INFERRED`, lines 26-31) — **confidence here means "how the finding was established," not "how sure are we the evidence is current/complete."** This is a naming trap for v1.3.0: a new "evidence certainty" concept must not reuse the word "confidence," which already means something else on `Finding`. (Also note `rollback.Recommendation` has its own, third, unrelated `Confidence` field — see Rollback section below. Three different "confidence" concepts already coexist in this codebase under different types; a fourth must not be added carelessly.)
- `ResourceReference` (lines 56-70): tagged union over `Plane` (`live`/`manifest`/`aws`, lines 36-40) — **this is the existing "evidence source" naming precedent.** `Plane` is scoped to *where a resource occurrence was observed*, not to catalog-derived or operator-supplied facts (there is no `PlaneCatalog` or `PlaneDerived`). `Validate()` (lines 94-115) enforces field combinations per plane.
- `OccurrenceKey()`/`ConceptKey()` (lines 119-162) — occurrence identity vs. cross-plane conceptual identity; deliberately returns `ok=false` for a manifest resource with no namespace ("apply-time namespace selection cannot be guessed safely," line 133-134) — another concrete precedent for "don't guess, return not-determinable."
- `Finding` struct (lines 205-246): no field today records whether the rule that produced it ran to completion, was partially blocked, or is itself a legacy/synthetic construct. Every finding that exists implies "the rule ran and found this" — there is no way to represent "the rule tried to run and could only partially inspect its subject."
- `Fingerprint`/`FingerprintV2` (lines 283-313): purely a function of rule ID, target version, discriminator, and resource concept/occurrence keys — **confirmed no message text or evidence-state field feeds the fingerprint** (matches the WH-005 invariant explicitly re-verified in v1.2.1; the same holds structurally for any new field, since `FingerprintV2`'s inputs are a fixed, short, explicit list, not a generic struct hash).

### Report model — `internal/findings/report.go`

- `CoverageStatus` = `complete` / `partial` / `skipped` (lines 13-19). `PlaneCoverage{Status, Errors []string}` and `ScanCoverage{Kubernetes, AWS, Manifests}` (lines 21-30) — **this is the only evaluation-state concept that exists today, and it is plane-scoped, not rule-scoped.**
- `NewReport`/`NewReportWithUpgradeContext` (lines 201-265) seed a **placeholder** coverage (`Kubernetes: complete`, `AWS: skipped`, `Manifests: skipped`, lines 227-231) before real collector results are known; callers must call `SetCoverage` (lines 279-282) once collection finishes, or `UpgradeReadiness` silently disagrees with `Result()` (documented failure mode at lines 267-278, confirmed already caught once in production: "a `--provider=eks` scan with missing IAM permissions exits 3/INCOMPLETE but would report `UpgradeReadiness.Verdict` `CLEAN`").
- `IsComplete()` (lines 812-816) and `resultAndExitCode()` (lines 785-796) key **only on `CoveragePartial`** — `CoverageSkipped` never affects `Result()`/`ExitCode()`. Confirmed by grep: no renderer, no rollback file, no TS schema branches on `== CoverageSkipped` anywhere in the codebase. This is a deliberate, uniform design (skipped = never attempted, benign) — not an oversight — but it means "skipped" carries zero visibility weight anywhere downstream, which matters once repeat-scan comparison needs to know a rule category was never attempted.
- `APICompatibilitySummary` and `UpgradeReadinessSummary` (lines 90-109, 427-440) are both explicitly documented as **derived from findings only** — never a second decision engine, never able to disagree with `Result()`. `UpgradeReadinessCategory.Status` (`Passed`/`Warning`/`Failed`, lines 434-440) has **no fourth "not evaluated" state** — a category whose rules never ran (because the required plane was skipped) reports `Passed`, identical in shape to a category that ran cleanly. This is the single clearest instance of the "no finding looks like healthy" gap the task asked to find.
- `categoryByRuleID` (lines 463-504) maps all 31 registered rule IDs to one of 10 categories; enforced complete by `internal/findings/upgrade_readiness_registry_test.go` (`TestEveryRegisteredRuleHasAnExplicitCategory` — **verified all 31 rules present, no gap**, contradicting an initial premise in this audit's own task brief that EKS-NG-001..004 might be missing; they are present at lines 489-492).
- `UpgradeApplicable()` (lines 701-710): defaults `true` whenever `CurrentVersion` is empty or unparseable — explicit "don't guess 'same version'" comment (lines 696-700) citing ADDON-002's `VerificationUnavailable` as the model precedent. This is a report-level applicability decision that already exists and already follows the right pattern; v1.3.0 should generalize this pattern, not replace it.
- `Coverage` is currently the **only** report-level evaluation-state surface; there is no rule-level or finding-level equivalent anywhere in `Report`.

### Rule execution and registration — `internal/rules/rule.go`, `internal/rules/defaults.go`

- `ScanContext{K8s, AWS, Manifests *Snapshot, UpgradeContext}` (`rule.go:21-26`): doc comment states the operative contract plainly — "AWS and Manifests are nil whenever that plane wasn't attempted or was gracefully skipped — rules that depend on them must check for nil and simply produce no findings, never error." **This is the exact mechanism that makes a not-applicable rule invisible: it returns zero findings, indistinguishable from "ran and found nothing."**
- `Registry.RunAll` (`rule.go:66-85`): loops every registered rule; **only the first rule's error is retained** as `firstErr` — every subsequent rule's error is silently discarded (its findings are dropped via `continue`, no trace of the error itself survives). Confirmed by direct code reading, not inferred. This means a rule that fails to evaluate today produces **no report-visible signal at all** unless it happens to be the first rule registered to fail.
- `NewDefaultRegistry()` (`defaults.go:6-40`): 31 rules, confirmed matching `internal/v1compat/contract.go`'s `ExpectedRuleIDs()` (31 entries, contract.go:358-367).
- `NewManifestsOnlyRegistry()` (`defaults.go:50-55`): registers **only API-001 and API-002**. Doc comment: "every other rule reads sc.K8s/sc.AWS directly and several (e.g. WH001, NODE001) don't nil-guard those fields... running them against a nil sc.K8s would panic, not just report nothing." **This means 29 of 31 rules are entirely absent — not not-applicable, not skipped-with-a-flag, simply never invoked — during every manifests-only scan.** There is no report field that says "29 rules did not run in this mode"; a manifests-only report's `UpgradeReadinessSummary` categories for Extension APIs, Admission Webhooks, Disruption Safety, Drain Readiness, Node Readiness, Add-ons, CoreDNS, Workload Health, EKS Upgrade Insights all show `Passed` with zero rule IDs populated, which is visually identical to "checked, nothing wrong." (Category list corrected to include Extension APIs during the decision-log verification pass — see "Verification of previously-unverified facts" item 5; the rule count of 29/31 was already correct.)
- Confirmed live landmine (not exploited today, but real): `internal/rules/node001.go:28` and `internal/rules/wh001.go:25` dereference `sc.K8s` with **no nil-guard**, unlike every other K8s-consuming rule in the codebase. Currently safe only because the manifests-only registry never invokes them; any future code path constructing a `ScanContext` with `K8s == nil` outside the `--manifests-only` CLI entry point would panic.

### Rule skip/failure behavior — inventory summary (full matrix in next section)

Confirmed patterns, by count out of 31 rules:
- **7 rules** (`WH-002`, `PDB-001`, `PDB-002`, `CRD-001`, `CRD-002`, `APISERVICE-001`, plus `ADDON-002` via a different mechanism) explicitly check `sc.K8s.Errors["<resource>"]` / `sc.AWS.Errors[...]` and either silently skip or (ADDON-002 only) produce a visible Warning.
- **~24 rules** have **no** Errors-map check at all — a partial collector failure for their specific resource (nodes, pods, deployments, webhooks, nodegroups, insights) is completely indistinguishable in the report from "evaluated cleanly, no problem found."
- **0 rules** have a distinct "not applicable" return value or field — "not applicable" and "evaluated, no problem" are the same code path (zero findings) everywhere in `internal/rules`.

### Compare semantics — `internal/comparison/compare.go`

- `Compare()` (lines 17-79) matches findings **only by `Fingerprint`** (`indexByFingerprint`, lines 81-93): present-in-current-only → `New`; present-in-both, changed → `Changed`; present-in-both-unchanged → `Unchanged`; present-in-baseline-only → `Resolved` (lines 70-74).
- **Confirmed: `Compare()` never reads `Report.Coverage` in its matching/bucketing logic.** A finding whose rule ran in the baseline scan but could not run in the current scan (AWS creds now missing, or a switch to `--manifests-only`) is bucketed as `Resolved`, identical in shape to a genuinely fixed issue. The only cross-report sanity checks present are a `TargetVersion` mismatch warning (lines 42-46) and an `UpgradeContext` mismatch warning (lines 47-51) — both surfaced as free-text `Warnings`, not as per-finding state.
- `LoadAndNormalize` (`normalize.go:32-56`) does faithfully preserve each report's own `Coverage` when backfilling legacy-schema documents, but nothing downstream in `internal/comparison` reads it back.
- `internal/gate/evaluate.go:43-47` **does** consult `baseline.IsComplete()`/`current.IsComplete()` and collapses the whole gate decision to `DecisionNeutral` + `ReasonInsufficientEvidence` if either is incomplete — confirming the codebase already has the *concept* of "not confident enough to decide," just applied only at the aggregate CI-gate level, never fed back into `comparison.Comparison`'s New/Resolved/Changed buckets themselves.

### JSON schema — `internal/findings/report.go` (`SchemaVersion = "1.0"`), `internal/report/json.go`

Frozen fields per `docs/v1-compatibility-contract.md:104-117`: findings schema `1.0`, plan schema `1.0`, action-plan `kubepreflight.io/upgrade-action-plan/v1`, comparison `kubepreflight.io/scan-comparison/v1`, API catalog `apicatalog.kubepreflight.io/v1`, add-on catalog `compatcatalog.kubepreflight.io/v1`. **The rollback assessment schema (`kubepreflight.io/rollback-assessment/v1alpha1`) is explicitly excluded from the stable-v1 guarantee** (contract doc lines 119-122, 185-190) — this is real headroom for v1.3.0 to evolve rollback's freshness/provenance shape further without a compatibility break, while the comparison schema is fully frozen and would need additive-only fields or a new version string.

### Terminal / Markdown / HTML rendering — `internal/report/terminal.go`, `markdown.go`, `html.go`, `view.go`

- Shared logic lives in `view.go`'s `coverageIssueLines()` (lines 195-214), called by all three renderers — it emits a line **only when a plane's `Status == CoveragePartial`**; `skipped` planes produce zero output in all three. Terminal (`terminal.go:73-86`) and Markdown (`markdown.go:44-51`) are functionally identical on every coverage question — both gate on `!r.IsComplete()` and both have no richer affordance.
- HTML (`html.go`) is strictly richer: an explicit `AWS enrichment: On/Off` chip (`awsEnrichment()`, lines 819-831) and two purpose-built "category unavailable" indicators — `showEKSNodegroups` suppression (lines 971-984) and `eksUpgradeInsightsUnavailable` (lines 1071-1081, rendered as literal text "EKS Upgrade Insights unavailable. Kubernetes findings are still valid." at line 1958). Terminal and Markdown have no equivalent — a CAB packet exported as Markdown or read from a terminal loses this honesty signal that the same scan's HTML report would show.
- None of the three renderers exposes rule-level (as opposed to plane-level) evaluation state, because no such state exists in the report model to render.

### Web Console schema and rendering — `web/src/lib/*.ts`, `web/src/components/*.tsx`

- `findings-schema.ts` mirrors `PlaneCoverage`/`ScanCoverage` field-for-field with Go (no drift found); `normalizeCoverage` defaults match `NewReport`'s Go defaults exactly.
- `comparison-schema.ts` has **no coverage concept at all** — diffs purely by fingerprint, same blind spot as the Go `comparison` package it mirrors.
- Only two components read `report.coverage`: `DecisionHero.tsx:83` (`incomplete = ...some(plane => plane.status === "partial")` — `skipped` never checked, same asymmetry as Go) and `SummaryTab.tsx:36-41` (the "Assessment incomplete" banner, same `partial`-only gate). `SummaryTab.tsx` also mirrors HTML's EKS-nodegroup/insights-unavailable messaging (lines 29-32, 252-253) — Console and HTML are a matched, richer pair; Terminal/Markdown are the plainer pair. This is a real, confirmed cross-surface split, not a hypothetical one.
- `RollbackReadinessTab.tsx` renders `reasonCodes`/`evidence` as opaque strings (lines 59-78) with no special-casing for stale/mismatch codes — the operator learns "stale" only by reading generated prose, not a structured signal the UI itself reacts to.

### Manifests-only behavior

Confirmed (`defaults.go:50-55` + `internal/cli`): only API-001/API-002 execute; `Coverage.Kubernetes`/`Coverage.AWS` are seeded `skipped` (benign, "never attempted") via `internal/cli/coverage.go:13-48`'s `kubernetesRequested`/`awsRequested` gating. **A manifests-only report and a live-cluster report both render an "UpgradeReadiness" scorecard with the same category list and the same `Passed` default status for every category no rule touched** — nothing in the rendered output tells an operator "9 of 10 categories were not evaluated in this mode" without them separately knowing the product's manifests-only design. **Correction from the decision-log verification pass (see "Verification of previously-unverified facts" item 5): this is 9 of 10 categories, not 8** — `categoryOrder` (`internal/findings/report.go:445-456`) lists 10 categories total; `NewManifestsOnlyRegistry()` (`defaults.go:52-53`) registers only API-001/API-002, both mapped to "API Compatibility" (`categoryByRuleID`, `report.go:464-465`). Every other category, **including "Extension APIs"** (CRD-001/CRD-002/APISERVICE-001, none of which run in manifests-only mode), has zero rules registered and therefore defaults to `Passed`. The original gap-4 list below omitted "Extension APIs" from its enumeration — a real discrepancy in the original audit, corrected here rather than silently overwritten.

### Live-cluster behavior / EKS provider behavior

`internal/collectors/aws/collector.go` is the real EKS enrichment path (not `internal/providers/eks`, which is a 15-line marker type — `eks.go:11-14` — with an explicit doc comment that it doesn't wrap or replace the AWS collector). ### Partial-access and infrastructure-failure handling

`internal/cli/collection_issue.go:40-95`'s `classifyCollectionIssue` is the one consistent classification point across all three collectors (k8s, AWS, manifest) — distinguishes timeout/cancelled/permission-denied/resource-unavailable/malformed-input/AWS-provider-failure, with AWS IAM permission-denied detected via `smithy.APIError` code substring matching (`"accessdenied"|"unauthorized"|"forbidden"`, lines 81-84). **All of this rich classification collapses into the same two-state `PlaneCoverage.Status` (`complete`/`partial`) once it reaches the report** — the permission-denied fact survives only as free text in `PlaneCoverage.Errors []string`, never as a structured field. Exit code 4 (infrastructure failure — "no trustworthy report was produced... OR a requested persistent report/artifact could not be created or fully written") is a distinct, separate concept from exit code 3 (`INCOMPLETE` — partial evidence, a report *was* produced) — confirmed in `docs/v1-compatibility-contract.md:44-52` and matches the v1.2.1 report-write-exit-code fix.

### Backward compatibility / legacy report handling

`internal/v1compat/contract.go` locks CLI paths, exit codes, schema identifiers, the 31 rule IDs, default priorities, and a specific `FingerprintV2` sample hash. `internal/comparison/normalize.go`'s `LoadAndNormalize` backfills legacy-schema documents, preserving `Coverage` faithfully (test: `TestLoadAndNormalize_IncompleteCoveragePreserved`). ## Confirmed product gaps

Each gap below is grounded in the baseline/inventory above; only new synthesis is added here.

1. **No finding can be misread as healthy.** `UpgradeReadinessCategory.Status` defaults `"Passed"` for a category whose rules never executed (`internal/findings/report.go:520` initializes every category to `Passed`; nothing downgrades a category whose constituent rules are absent from the registry, e.g. manifests-only mode). A manifests-only scan's HTML/Console/terminal "Admission Webhooks: Passed" line is factually indistinguishable from a live scan that ran WH-001/002/004/005 and found nothing. **File:line:** `internal/findings/report.go:518-547` (no absent-category branch); `internal/rules/defaults.go:50-55` (registry composition that causes the absence).
2. **A skipped rule is invisible.** Confirmed structurally: rules return `([]Finding{}, nil)` for both "ran, nothing wrong" and "not applicable to this input"; `Registry.RunAll` (`rule.go:66-85`) has no per-rule "did this run" bookkeeping of any kind — it returns a flat `[]Finding`, discarding which of the 31 registered rules contributed how many findings, let alone which of the 31 didn't run at all in a given `ScanContext`.
3. **A provider check that cannot run doesn't clearly expose it at rule granularity.** `ADDON-002`'s pair of explicit "unknown/unverifiable" mechanisms is the *exception*, not the norm — 29 of 31 rules have no such mechanism (see inventory). Even where `sc.AWS == nil` (no AWS enrichment attempted at all), rules like `NODE-002`/`NET-002`/`EKS-NG-*`/`EKS-INSIGHT-*` simply return no findings; the only downstream signal is the plane-level `Coverage.AWS.Status`, which a reader must separately correlate back to "therefore these 9 rules didn't run" — nothing in the report does that correlation for them.
4. **Manifests-only mode lacks evidence but can appear equivalent to a live scan in the scorecard.** Directly demonstrated by gap 1: `UpgradeReadinessSummary.Categories` for a manifests-only scan and for a live scan both use the identical `Passed`/`Warning`/`Failed` vocabulary with no fourth state, and **9** of 10 categories (`Extension APIs`, `Admission Webhooks`, `Disruption Safety`, `Drain Readiness`, `Node Readiness`, `Add-ons`, `CoreDNS`, `Workload Health`, `EKS Upgrade Insights` — corrected list, see item 5 in "Verification of previously-unverified facts": the original count of 8 omitted `Extension APIs`) will read `Passed` in every manifests-only report regardless of what a live scan would have found.
5. **Access-denied behavior produces an incomplete conclusion, correctly at the plane level, but the specific cause is demoted to prose.** `classifyCollectionIssue` (`internal/cli/collection_issue.go:40-95`) does the hard work of identifying AWS IAM permission-denied specifically, but `buildScanCoverage` (`internal/cli/coverage.go:13-48`) flattens this into `CoveragePartial` plus a free-text `Errors []string` entry — permission-denied and "AWS API is down" and "one nodegroup's `describe-nodegroup` call timed out" are all the same structured state (`partial`), differing only in a string a machine reader would have to pattern-match to recover.
6. **Compare may interpret missing evaluation as resolved.** Directly confirmed: `Compare()` (`internal/comparison/compare.go:70-74`) buckets any fingerprint present in the baseline and absent from the current scan as `Resolved`, with zero check of whether the responsible rule/plane was even evaluated in the current scan. This is the single most consequential gap for the "regular usage" goal: a team that runs a full live scan today and a `--manifests-only` scan next week (or hits an AWS permissions regression) will see their WH-005/PDB-002/ADDON-002/etc. findings reported as "Resolved" in the compare output, when nothing was actually fixed.
7. **Console and CLI interpret the same state consistently with each other, but both interpret `skipped` the same *blind* way.** This is a partial disconfirmation of the task's premise: HTML and Console are a matched, richer pair (EKS-nodegroup/insights-unavailable messaging, AWS-enrichment chip); Terminal and Markdown are a matched, plainer pair. All four agree that `skipped` coverage triggers no visible signal anywhere. So the actual gap is not "CLI vs. Console disagree" (they don't, confirmed) but "Terminal/Markdown lose real information that HTML/Console already compute and could show" — a rendering-parity gap, not a semantics gap.
8. **A rule-level uncertainty is currently represented only through message prose, with exactly one exception.** `ADDON-002`'s `addonVerificationError`/`addon002CatalogMissingFinding` (`internal/rules/addon001.go:219-230, 414-446`) is the sole rule-level "unknown/unverifiable" state expressed as a real, filterable Warning finding rather than only as evidence text. Every other rule's uncertainty (unparseable kubelet version in NODE-001, EKS Upgrade Insights total-API-failure, WH-002's own explicit skip) is either silent or, at best, a sentence inside `Finding.Evidence`/`Message` — not a field a renderer or `compare` could branch on without string-matching.
9. **`RunAll`'s error-swallowing is a systemic, currently-unexploited risk that compounds every gap above.** Confirmed at `internal/rules/rule.go:66-85`: only the very first rule (in fixed registration order, `API-001` first) to return an error is retained; every subsequent rule's error is fully discarded, its only trace being that its findings are dropped. A real rule-evaluation failure for rule #2 through #31 today produces **zero** report-visible signal — not a Warning, not a coverage change, nothing.
10. **The `UpgradeGate` enum has no "not applicable" value**, only `block`/`allow`/`operator_decision`, with empty string as a legacy fallback that resolves through severity (`internal/findings/context.go:74-99`, `EffectiveUpgradeGate` at lines 91-99). "This rule's gate concept doesn't apply" and "this rule's gate evaluated to allow" are the same value (`allow`) today — a real ambiguity if v1.3.0 wants gate-level applicability to be explicit.

## Candidate data-model options

Existing naming conventions to build from, confirmed in the baseline: `ResourceReference.Plane` (`live`/`manifest`/`aws`, snake-free lower-case single words), `CoverageStatus` (`complete`/`partial`/`skipped`, lower-case single words), `compatcatalog.Status` (`compatible`/`incompatible`/`upgrade-recommended`/`unknown`, hyphenated lower-case), `rollback` package's `CheckStatus` (**verified during the decision-log pass, see "Verification of previously-unverified facts" item 1** — exact values are `pass`/`warning`/`fail`/`unknown`, `internal/rollback/model.go:188-191`; note this is **four** values, not the three (`pass`/`fail`/`unknown`) this document originally guessed, since `CheckWarning = "warning"` also exists), `UpgradeGate` (`block`/`allow`/`operator_decision`, snake_case for multi-word). The codebase's convention is consistently **lower-case, terse, and either single-word or snake_case for multi-word** — not upper-case constants like `NOT_EVALUATED`. Any new enum should follow this casing exactly.

Three shape options were considered:

**Option A — extend `PlaneCoverage`/`ScanCoverage` granularity only (plane-level, no new axis).** Add nothing new; instead make `Coverage.Kubernetes/AWS/Manifests.Status` finer (e.g. distinguish `partial` sub-reasons). **Rejected**: this does not solve gap 1/2/6 above, since those gaps are about *which rules* ran, not *which planes* were touched — a plane can be `complete` while several of its rules still didn't run for reasons unrelated to collection failure (e.g. `NewManifestsOnlyRegistry`'s registry-composition exclusion has nothing to do with `Coverage.Kubernetes.Status`, which is `skipped` regardless of which specific rules would have been registered).

**Option B — a single new per-rule `EvaluationState` field, attached to a new lightweight `RuleExecution` record on `Report` (not on `Finding`).** One `[]RuleExecution{RuleID, State, Reason}` list on `Report`, where `State` is one of a small closed set (see recommendation below). Findings themselves are unchanged. **Recommended** — see next section for why.

**Option C — evaluation state as a field on every `Finding`, including a new synthetic "no-finding-marker" finding per not-run rule.** Rejected: would require inventing a finding that isn't a finding (a rule with zero real findings would need a placeholder `Finding{RuleID, EvaluationState: "not_evaluated"}` object just to carry the state), which pollutes `Summary`/`Fingerprint`/severity semantics that assume every `Finding` is a real risk observation. This also risks exactly the "unknown status becomes meaningless alert noise" failure mode the task explicitly warns against.

**Decision (open for reviewer confirmation, see "Open decisions"):** Option B. One field is not sufficient — applicability and execution are logically distinct (a rule can be *applicable* but *fail* to execute, or *not applicable* and therefore never attempt execution) — so `RuleExecution` needs two axes, not one:
- `Applicability`: whether this rule's preconditions were met for this scan's inputs — e.g. `applicable` / `not_applicable` (the plane/provider/resource this rule needs simply isn't part of this scan's scope, by design — e.g. API-only rules in a manifests-only scan are "not applicable" in the mode sense, not "failed").
- `Execution`: whether an applicable rule actually completed — `evaluated` / `not_evaluated` / `insufficient_evidence` (ran, but its required collector data was itself partial/errored) / `failed` (returned a Go error).

This two-axis split directly generalizes the existing `ADDON-002` pattern (`Compatible`/`Incompatible`/`Unknown` decided separately from "did we even get to check") and the existing rollback freshness-gate pattern (`Fresh`/`Stale`/`Unknown`/`NotApplicable` — four states across two logical questions: "is there evidence" and "is it good enough"), rather than inventing new vocabulary.

## Recommended v1.3.0 contract

**Evidence source:** do not add a new enum. `ResourceReference.Plane` (`live`/`manifest`/`aws`) already names *where* evidence came from for anything resource-shaped; catalog-derived facts already have their own home (`apicatalog`/`compatcatalog` `Source`/`Confidence`/`LastVerifiedDate` fields, confirmed present on `VersionedCatalog` entries). v1.3.0 does not need a fifth "evidence source" taxonomy — it needs the *execution* taxonomy below, which is orthogonal to plane.

**Evaluation state — two fields, not one**, attached to a new `Report.RuleExecutions []RuleExecutionRecord` (per rule ID, not per finding):
```go
type RuleApplicability string
const (
    ApplicabilityApplicable    RuleApplicability = "applicable"
    ApplicabilityNotApplicable RuleApplicability = "not_applicable"
)

type RuleExecutionState string
const (
    ExecutionEvaluated            RuleExecutionState = "evaluated"
    ExecutionNotEvaluated         RuleExecutionState = "not_evaluated"          // rule not registered/run for this scan mode
    ExecutionInsufficientEvidence RuleExecutionState = "insufficient_evidence"  // ran, but required collector data was partial
    ExecutionFailed               RuleExecutionState = "failed"                // rule returned a Go error
)

type RuleExecutionRecord struct {
    RuleID        string             `json:"ruleId"`
    Applicability RuleApplicability  `json:"applicability"`
    State         RuleExecutionState `json:"state"`
    Reason        string             `json:"reason,omitempty"`
}
```
Rationale for two fields: collapsing them (Option C-style single field) cannot represent "not applicable in this mode" (a design fact, known before the scan even starts, e.g. manifests-only) separately from "applicable but the collector failed" (a runtime fact, discovered during collection) — these need different operator responses (the first is expected and requires no action; the second is a real coverage gap requiring investigation or a rerun). This mirrors the rollback gate's own precedent of stacking independent yes/no questions (identity match, freshness) rather than one combined enum.

**Observation metadata: `observedAt`/`freshness`/`staleAfter` — do NOT add report-wide or rule-wide, based on what Phase 1-3 found.** The rollback provenance chain (PR #209) already solved this narrowly for one case (`report.ScannedAt` vs. rollback's own `GeneratedAt`, 24h threshold, `Fresh`/`Stale`/`Unknown`/`NotApplicable`). Generalizing it further in v1.3.0 is **not justified** by anything found in this audit:
- `Report.ScannedAt` already exists and is already the timestamp every freshness question needs — a *second* per-rule or per-finding timestamp would be redundant, since every rule in a single scan shares one `ScannedAt`.
- The real gap this audit found is not "we don't know when evidence was collected" (we do — `ScannedAt`) but "we don't know whether a rule ran at all" (the `RuleExecutionRecord` above). Adding `observedAt` per rule would not fix any of the ten confirmed gaps; it would only be useful once cross-scan history/scheduling exists (v1.4.x+), where "is baseline itself stale relative to now" becomes a real question the rollback gate already answers for its one case.
- **staleAfter as a configurable per-family threshold** is explicitly deferred in the rollback code itself ("family-specific thresholds and a CLI override... to later work," inferred from `internal/rollback/operational.go`'s comments per the research pass — **unverified**, doc text in `docs/rollback-readiness.md` was not read directly in this pass and should be confirmed before finalizing). Given it's already deferred in the one place that has real freshness logic today, v1.3.0 should not pull it forward for the whole report.
- **Recommendation: v1.3.0 adds no new timestamp field.** `RuleExecutionRecord` needs no `observedAt` of its own — `Report.ScannedAt` plus `Coverage.*.Errors` already carries what's needed to explain *why* a rule is `not_evaluated`/`insufficient_evidence`. Revisit timestamp granularity only when v1.4.x's "what changed since last scan" needs to reason about two different scans' relative ages, which is a `comparison`-package concern (comparing two `ScannedAt` values), not a per-rule concern.

**Scope granularity:** rule-level, on `Report`, not on `Finding` and not only on `Coverage`. Justification: `Coverage` is too coarse (plane, not rule — gap 1/2/3/4/6 all trace back to this); `Finding`-level would require synthetic non-finding findings (Option C, rejected above) and would duplicate the same state across every finding a rule happens to produce, when the state is a property of the *rule's run*, not of each individual finding. A `Report`-level list keyed by rule ID is the smallest surface that resolves every confirmed gap without duplicating state across layers.

## Compatibility and schema strategy

Per-item impact analysis, per Phase 5's explicit checklist:

- **Rule IDs:** unchanged. No rule ID added, removed, or renamed.
- **Severity:** unchanged. `RuleExecutionRecord` is orthogonal to `Finding.Severity`.
- **Upgrade gates:** unchanged (`UpgradeGate` enum untouched in the selected scope; see deferred item on adding a "not applicable" gate value).
- **Impact scopes:** unchanged.
- **Readiness score / compatibility score:** `UpgradeReadinessSummary`/`APICompatibilitySummary` remain derived from findings only, per their existing documented invariant (`report.go:85-87, 419-424`) — this must continue to hold; a category with rules `not_evaluated` should NOT be silently scored as `Passed` in a way that inflates `ReadinessScore` versus a category genuinely checked clean. **Recommendation:** `ReadinessScore` computation is out of scope for a numeric change in v1.3.0 (no penalty/bonus for not-evaluated categories) — only the *display* changes (badge), to avoid a confusing score swing tied to a semantics-only release. This should be called out explicitly to reviewers as a deliberate non-change (see "Open decisions" — a strong argument exists either way).
- **Operator decision counts:** unchanged; `RuleExecutionRecord` doesn't produce operator decisions itself.
- **Exit codes:** unchanged. `not_evaluated`/`insufficient_evidence` states do not, by themselves, change `Result()`/`ExitCode()` — `IsComplete()` continues to key off `CoveragePartial` only, per the existing (deliberately narrow) design. A rule-level `insufficient_evidence` should very likely *also* correspond to a `CoveragePartial` plane already (since the underlying cause is a collector error), so this shouldn't practically diverge from today's exit-code behavior — but this equivalence should be tested explicitly, not assumed.
- **Fingerprints:** unchanged and explicitly re-verified not to be affected — `FingerprintV2`'s input list (`ruleID, targetVersion, discriminator, resource keys`) has no path to `RuleExecutionRecord` or any new field; the WH-005 invariant ("message text is not a fingerprint input") holds structurally the same way for this new field, since it isn't on `Finding` at all.
- **Compare behavior:** intentionally changes (capability 3) — this is the one deliberate behavior change in the whole release, and it is additive (new bucket) rather than a redefinition of existing buckets.
- **JSON schema:** additive-only bump on `Report` (new field) and comparison output (new bucket) — both need explicit versioning decisions logged in `docs/v1-compatibility-contract.md` before implementation, since findings schema `1.0` and comparison schema `v1` are both currently frozen surfaces.
- **Markdown/HTML/terminal reports:** prose-only additions, explicitly outside the frozen-surface list (`docs/v1-compatibility-contract.md:192`: "prose-only copy in terminal, Markdown, and HTML reports" is intentionally unstable).
- **Console compatibility:** additive TS schema fields; existing Console builds ignoring the new field continue to render exactly as before. **Correction from the decision-log verification pass** (see "Verification of previously-unverified facts" item 6): `web/src/lib/findings-schema.ts` does **not** use Zod at all — there is no `zod` import anywhere in `web/src/` and no `zod` dependency in `web/package.json`. The tolerant-defaulting behavior is hand-written: `parseFindingsDocument`'s top-level parse (lines ~198-230) only hard-requires `findings[]` to be an array (throws otherwise); every other field goes through a per-field normalizer (`stringOr(raw.x, fallback)`, `normalizeCoverage`/`normalizePlaneCoverage` at lines 1193-1206, etc.) that substitutes a safe default — never a parse failure — when the field is absent or malformed. `normalizeCoverage`'s defaults (`kubernetes` falls back to `"complete"`, `aws`/`manifests` fall back to `"skipped"`) match `NewReport`'s Go-side defaults exactly, confirming the original claim's substance even though the Zod-specific framing was inaccurate. The same manual-normalizer pattern (not `.optional()`/`.default()`) should be used for `ruleExecutions`.
- **Legacy reports:** `LoadAndNormalize` backfills a legacy (pre-1.3.0) report's absent `RuleExecutions` per-rule, from finding presence, never as a blanket "all applicable rules evaluated." The invariant: a legacy finding present for a rule → `applicable`/`evaluated`; no finding for a current rule → `applicable`/`not_evaluated`. Absence of a legacy finding is never inferred as an evaluated-clean pass — the opposite of that inference is the entire point of this backfill, since a blanket "evaluated" default would let a rule that never actually ran on the old scan read as a genuine clean result today.
- **GitHub Actions:** no flag/output contract changes anticipated; `action.yml`'s existing outputs (exit code, report paths) are unaffected. **Verified** (see "Verification of previously-unverified facts" item 4): `action.yml`'s full `outputs:` block (repo root, lines 53-77) declares exactly `verdict`, `blockers`, `warnings`, `operator-decisions`, `readiness-score`, `can-upgrade-continue`, `findings-file`, `report-file` — all scan-level aggregates or file paths, none category-level or rule-level. No output would need to change for `RuleExecutionRecord`/`not_re_evaluated` to land.
- **Manifests-only workflows:** this is the primary beneficiary, not a compatibility risk — manifests-only reports become explicitly self-documenting about their own narrower rule coverage for the first time.
- **Rollback reports:** unaffected (rollback schema is explicitly unstable/`v1alpha1` and has its own, already-superior, provenance model that this release does not touch).

function normalizePlaneCoverage(value: unknown, fallback: PlaneCoverage["status"]): PlaneCoverage {

}

## Lock semantic rules — release invariants

The following are locked as explicit release invariants for v1.3.0, per reviewer instruction. These generalize the reasoning already present in "Confirmed product gaps," "Recommended v1.3.0 contract," and "Compatibility and schema strategy" above into a single enforceable checklist:

- No finding + `evaluated` = the rule found no reportable issue.
- No finding + `not_evaluated` ≠ safe.
- A baseline finding absent from the current report is `resolved` only when the responsible rule was `evaluated` in the current scan.
- A baseline finding absent when the rule was `not_evaluated` becomes `not_re_evaluated`.
- Rule-level failure remains distinct from a product finding, unless a rule intentionally emits an unverifiable finding (the `ADDON-002` pattern — `internal/rules/addon001.go:219-230,414-446`).
- Infrastructure failure remains distinct from incomplete rule evaluation (exit code 4 vs. exit code 3/`INCOMPLETE`, per `docs/v1-compatibility-contract.md:54-60`).
- Rule-execution metadata must not affect finding fingerprints (`FingerprintV2`'s fixed input list — rule ID, target version, discriminator, resource keys — has no path to `RuleExecutionRecord`; re-verified during this pass, no new fingerprint input introduced by anything in this document).
- Existing rule severities, upgrade gates, and impact scopes remain unchanged.
- Legacy normalization must not silently claim native evaluation certainty — it must be possible to tell native (`1.1`+, present in the original document) from backfilled (`LoadAndNormalize`-filled for a legacy `1.0` document) `RuleExecutions` data. See Decision 2's recommended explicit marker.
