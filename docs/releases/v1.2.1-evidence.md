## Transient infrastructure failure and retry (classified, not a product defect)

- First run of `verify-go-install` failed with:

      go: github.com/imneeteeshyadav98/kubepreflight/cmd/kubepreflight@v1.2.1: verifying module:
      github.com/imneeteeshyadav98/kubepreflight@v1.2.1: reading https://sum.golang.org/lookup/...: 500 Internal Server Error

- This is Go's public checksum database (`sum.golang.org`) returning a 500 immediately after the new tag was pushed — a known propagation-lag pattern, not caused by anything in this repository's code, workflow, or release contents. The exact same failure mode, with the exact same resolution, occurred on the `v1.2.0` release one day prior.
- All other jobs (verify, all 5 platform binary builds, docker build/scan/publish, github-release creation, verify-published-release-{linux,windows,macos}, verify-published-container) succeeded on the first attempt — only the post-release `go install` sanity check was affected.
- Resolution: `gh api -X POST repos/imneeteeshyadav98/kubepreflight/actions/runs/<id>/rerun-failed-jobs`, re-ran only the failed job; it passed cleanly once `sum.golang.org` had caught up (a matter of minutes).
- Classification: **transient external infrastructure delay, not a KubePreflight defect.** No code, workflow, or release-process change is warranted from this; it is now an established, recognized pattern across two consecutive releases (v1.2.0 and v1.2.1), worth keeping in mind for future releases but not worth engineering around (a wait-and-retry runbook note is sufficient, matching the existing `CONTRIBUTING.md` guidance philosophy already established for a different, unrelated propagation-delay scenario earlier in this project's history).
